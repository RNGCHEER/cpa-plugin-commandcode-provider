# CommandCode Go / GOAT / Pro 套餐适配说明

> 对应提交：`RNGCHEER/cpa-plugin-commandcode-provider` `581fa9b`（v0.1.1）
> 适用：CLIProxyAPI v8 原生动态插件 `commandcode-provider`

---

## 1. 为什么要做这个适配

Command Code 对外有两个完全不同的通道，按账号套餐分流：

| 通道 | 地址 | 适用套餐 | 协议 |
| --- | --- | --- | --- |
| **Provider API** | `https://api.commandcode.ai/provider/v1`<br>（`/chat/completions`、`/models`） | 仅 **Provider** 档（付费 API 档） | OpenAI 兼容 |
| **CLI 私有网关** | `https://api.commandcode.ai/alpha/generate` | **Go / GOAT / Pro**（订阅档） | CLI 自己的信封 + 逐行 JSON 事件流 |

订阅档打 Provider API 会被直接拒绝：

```
HTTP 403
{"error":{"code":"upgrade_required",
          "message":"Your Go plan doesn't include API access. Upgrade to Provider..."}}
```

`upgrade_required` 这个 code 是**唯一**的判断信号 —— 不看套餐名、不写死套餐表，也不依赖任何本地配置。

原插件（v0.1.0）只实现了 Provider API，所以 Go 账号的表现是：**模型能列出来、一发请求就 403**：

```
403 upstream execution failed: provider=commandcode model=commandcode/gpt-5.4
err={"error":{"message":"Your Go plan doesn't include API access. Upgrade to Provide...}}
```

v0.1.1 补上了 CLI 网关通道。

---

## 2. 判定与回退逻辑

对**每一把凭证**独立判定，先试 Provider API，再按结果决定：

```
对凭证 K：
  ├─ 若 K 已标记为「仅网关」 ─────────────────► 直接走 CLI 网关
  └─ 否则 POST {base-url}/chat/completions
       ├─ 2xx ─────────────────────────────────► 返回（reasoning 回填）
       ├─ 403 upgrade_required ────────────────► 标记 K 为「仅网关」
       │                                          用同一把 key 改走 /alpha/generate
       ├─ 401/402/429/5xx/传输错误 ────────────► 换下一把 key
       └─ 400/404/413/422 ─────────────────────► 请求本身的问题，直接返回
```

几个要点：

- **按凭证记账**：标记只挂在那一把 key 上，Provider 档 + Go 档混用时各走各的，不会互相干扰。
- **只降级一次**：首次命中 `upgrade_required` 后记住该凭证，之后不再白跑一次 403。
- **流式同样适用**，且只在首字节之前切换；一旦 2xx 流建立，已投递字节无法回滚。
- 网关侧失败仍按原有可重试分类切换下一把 key（网关的 429/5xx 与传输错误照常 failover）。

## 3. CLI 网关协议（实测）

以下都是对着真实账号（`individual-go-v1`）打出来的结果，不是推测。

### 3.1 请求

`POST https://api.commandcode.ai/alpha/generate`

**Headers**

| 头 | 值 |
| --- | --- |
| `Content-Type` | `application/json` |
| `Authorization` | `Bearer <user_... key>` |
| `User-Agent` | `cli` |
| `x-command-code-version` | CLI 版本，如 `1.84.0`（需跟随 npm `command-code`） |
| `x-cli-environment` | `production` |
| `x-project-slug` | 工作目录 slug（如 `my-project`） |
| `x-taste-learning` | `true` |
| `Accept` | `text/event-stream` |

**Body**

```jsonc
{
  "config": {
    "workingDir": "D:/my-project",
    "date": "2026-10-19",
    "environment": "windows-amd64",   // 注意：必须是字符串，传对象会 400
    "structure": [],
    "isGitRepo": false,
    "currentBranch": "",
    "mainBranch": "",
    "gitStatus": "",
    "recentCommits": []
  },
  "memory": null,
  "taste": null,
  "skills": null,
  "params": {
    "model": "deepseek/deepseek-v4-flash",   // 目录里的 catalog id，不带 commandcode/ 前缀
    "messages": [ /* 见 3.2 */ ],
    "tools": [ /* 见 3.3 */ ],
    "system": "系统提示（客户端传的），可为空串",
    "max_tokens": 4096,
    "stream": true,
    "temperature": 0.7,              // 可选
    "reasoning_effort": "high"       // 可选
  },
  "threadId": "ffb42a11-4f48-4a31-a491-361a6d5a157d"   // UUID v4
}
```

> `stream` 插件固定传 `true`：网关只按事件流返回，非流式请求由插件把整条流聚合成一个响应。

### 3.2 消息联合体（最容易踩的一环）

`params.messages[].role` 只接受 `user` / `assistant` / `tool`，**系统提示必须放到 `params.system`**，放进 messages 会 400：

```
Invalid option: expected one of "user"|"assistant" at "params.messages[0].role"
```

三种形状：

```jsonc
// user：content 可以是字符串，也可以是 part 数组
{ "role": "user", "content": "hi" }
{ "role": "user", "content": [
    { "type": "text",  "text": "看图" },
    { "type": "image", "image": "data:image/png;base64,...", "mimeType": "image/png" }
] }

// assistant：content 必须是 part 数组，可同时含 thinking / 文本 / 工具调用
{ "role": "assistant", "content": [
    { "type": "reasoning", "text": "上一轮的想法" },
    { "type": "text",      "text": "我来查一下" },
    { "type": "tool-call", "toolCallId": "call_00_abc", "toolName": "get_weather", "input": {"city":"Beijing"} }
] }

// tool：工具结果，content 必须是 tool-result 数组
{ "role": "tool", "content": [
    { "type": "tool-result", "toolCallId": "call_00_abc", "toolName": "get_weather",
      "output": { "type": "text", "value": "Beijing: 18C, clear" } }
] }
```

- `thinking` 块要以 `reasoning` 回放，否则思考类模型的多轮会退化。
- **调用与结果必须配对**：assistant 里发起但没拿到结果的 `tool-call`，插件会补一条 `output.type = "error-text"` 的合成结果。
- 连续的工具结果会合并进**同一个** `role:"tool"` 消息。
- **`call_id` 上限 64 字符**，超长会被 400 拒（`input[N].call_id`）。插件会确定性截断并保持配对一致。

### 3.3 tools

形状是 `{type,name,description,input_schema}`（**不是** OpenAI 的 `{type,function:{...}}`）：

```jsonc
{ "type": "function", "name": "get_weather",
  "description": "Get weather", "input_schema": { "type": "object", "properties": { ... } } }
```

传 OpenAI 形状会 400：

```
Invalid input: expected string, received undefined at "params.tools[0].name";
Invalid input: expected record, received undefined at "params.tools[0].input_schema"
```

网关另外内建 `web_search` / `web_fetch`，插件对非 function 的 tool 原样透传。

### 3.4 响应事件流

`Content-Type: text/event-stream`，但实际是**逐行 JSON（NDJSON）**，没有 `data:` 前缀，也没有 `[DONE]`：

```jsonc
{"type":"start"}
{"type":"start-step","request":{"body":{ ...实际生效的请求... }},"warnings":[]}
{"type":"reasoning-start","id":"reasoning-0"}
{"type":"reasoning-delta","id":"reasoning-0","text":"The"}
{"type":"reasoning-end","id":"reasoning-0"}
{"type":"text-start","id":"txt-0"}
{"type":"text-delta","id":"txt-0","text":"hello"}
{"type":"text-end","id":"txt-0"}
{"type":"tool-input-start","id":"call_00_abc","toolName":"get_time","dynamic":false}
{"type":"tool-input-delta","id":"call_00_abc","delta":"{}"}
{"type":"tool-input-end","id":"call_00_abc"}
{"type":"tool-call","toolCallId":"call_00_abc","toolName":"get_time","input":{}}
{"type":"finish-step","finishReason":"stop","rawFinishReason":"stop","usage":{ ... }}
{"type":"finish","finishReason":"stop","rawFinishReason":"stop","totalUsage":{ ... }}
{"type":"provider-metadata","providerMetadata":{"novita":{ ... }}}
```

| 事件 | 含义 | 插件动作 |
| --- | --- | --- |
| `start` / `start-step` / `*-start` / `*-end` / `provider-metadata` | 生命周期与元信息 | 忽略 |
| `reasoning-delta` | 思考增量 | → `delta.reasoning_content` |
| `text-delta` | 正文增量 | → `delta.content` |
| `tool-input-start` / `-delta` / `-end` | 工具调用流式参数 | → `delta.tool_calls[]`（index / id / name / arguments） |
| `tool-call` | 工具调用最终确认 | 补全 name 与 arguments（已流过的就不重复发） |
| `finish-step` / `finish` | 结束原因 + 用量 | 发终止 chunk（`finish_reason` + `usage`） |
| `error` | 流内错误 | 关流并把消息透传给下游 |

`finishReason`：`stop` / `tool-calls` / `length`（插件映射为 OpenAI 的 `stop` / `tool_calls` / `length`）。

用量字段：

```jsonc
{ "inputTokens": 44,
  "inputTokenDetails": { "noCacheTokens": 44, "cacheReadTokens": 0 },
  "outputTokens": 17,
  "outputTokenDetails": { "textTokens": 3, "reasoningTokens": 14 },
  "totalTokens": 61 }
```

### 3.5 错误

```jsonc
HTTP 400
{ "success": false,
  "error": { "code": "BAD_REQUEST", "status": 400,
             "message": "...HINT: Validation error: ...",   // 校验失败原因写在这里
             "docs": "https://commandcode.ai/docs/reference/errors/bad_request" } }
```

排错时优先看 `error.message` 里的 `HINT:` —— 它会把**第几个字段**、**期望什么类型**直接写出来。

## 4. 翻译细节（每个来回都做了什么）

### 请求方向（OpenAI chat-completions → 网关）

| 项 | 处理 |
| --- | --- |
| `model` | 剥掉 `commandcode/` 前缀，用目录 catalog id |
| `role:"system"` 消息 | 上提到 `params.system`（多条用 `\n\n` 连接），**不进 messages** |
| `role:"developer"` | 降级为 `user` 保留在对话里（宿主的中途提示，语义不同于系统提示） |
| 文本内容 | 字符串 → 字符串；part 数组 → `[{type:"text"}]` |
| 图片 | `image_url` → `{type:"image", image:<url>, mimeType:<从 data URL 解析>}` |
| `reasoning_content` / `reasoning` | → assistant 的 `{type:"reasoning"}` 块（回放历史思考） |
| `tool_calls` | → assistant 的 `{type:"tool-call"}`，`arguments` 字符串解析成对象 |
| `role:"tool"` | → `{role:"tool", content:[{type:"tool-result",...}]}`，同名的连续结果合并 |
| 未配对调用 | 补合成 `error-text` 结果 |
| `call_id` > 64 字符 | 确定性截断 + 哈希后缀，调用与结果共用同一映射表 |
| `tools` | OpenAI function → `{type,name,description,input_schema}`；其它原样透传 |
| `max_tokens` | 未给 = 64000；超过该模型目录 `maxOutputTokens` 时按目录钳制 |
| 其它字段 | `response_format` / `tool_choice` / `stream_options` 等一律丢弃（网关 schema 会拒未知字段） |

### 响应方向（网关事件流 → OpenAI）

| 项 | 处理 |
| --- | --- |
| `reasoning-delta` | → `choices[0].delta.reasoning_content` |
| `text-delta` | → `choices[0].delta.content` |
| `tool-input-*` / `tool-call` | → `choices[0].delta.tool_calls[]` |
| `finish` | → 终止 chunk：`finish_reason` + `usage`（含 `prompt_tokens_details.cached_tokens`） |
| 非流式调用 | 整条 NDJSON 聚合成一个 `chat.completion`（`message.content` + `message.reasoning_content` + `message.tool_calls`） |
| `[DONE]` | 不补发（与 Provider 路径一致，由宿主负责终结帧） |

## 6. 配置项

`plugins.configs.commandcode-provider` 下新增三项，**都可省略**，默认行为就是上面描述的逻辑：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `generate-url` | `{base-url 去掉 /provider/v1}` + `/alpha/generate` | CLI 网关地址，换镜像/自建时用 |
| `cli-version` | `1.84.0` | `x-command-code-version`，**需跟随 npm `command-code` 版本** |
| `working-dir` | 核心进程工作目录 | 上报给网关的项目目录（影响 `x-project-slug`） |

原有 `base-url` / `api-keys` / `plan-filter` / `visible-models` 等不变。`plan-filter: go` 只发布 Go 档可用的模型（按目录的 `minimumPlan` 过滤），与通道选择无关。

## 7. 验证

**单元测试**：`go test ./internal/plugin/`，覆盖 `upgrade_required` 识别、信封构造、消息联合体转换、事件流翻译、id 截断。

**联调实测**（`/v1/chat/completions`，客户端 key 打 CPA）：

| 用例 | 结果 |
| --- | --- |
| 非流式 | `200`，正文正确 |
| 流式 | `200`，OpenAI 分块 + `finish_reason: stop` + usage（含 cached_tokens） |
| 系统提示 | 传「只回 BANANA」→ 回 `BANANA`（客户端系统提示生效） |
| 函数调用 | `finish_reason: tool_calls`，`tool_calls` 参数正确 |
| 工具多轮 | assistant `tool_calls` + `role:"tool"` 结果回放 → `200` `stop`，答出工具结果 |

## 8. 已知限制

1. **`/v1/messages`（Claude 客户端）不可用**：注册时 `executor_output_formats` 声明了 `openai`/`claude`/`openai-response` 三种，宿主据此认为执行器会说 Claude、不再翻译；而执行器实际只输出 OpenAI chat-completions，Claude 客户端会收到 OpenAI 结构（流式还会以 `upstream stream closed before message_stop` 结束）。`/v1/chat/completions` 正常。
2. **`/alpha/generate` 是 CLI 内部端点**：不在公开文档里，协议随 `command-code` 版本漂移，`cli-version` 要跟着更新。
3. **网关会附加自己的 agent 系统提示**：`params.system` 为空串时上游注入 Command Code 自己的提示；传了系统提示就以客户端的为准。
4. **网关可能改写模型 id**：实测请求 `deepseek/deepseek-v4-flash`，`start-step` 回显的实际模型是 `deepseek/deepseek-v4.1-flash`（服务端策略决定）。
5. **`config.environment` 必须是字符串**：传对象会被 400 拒（`expected string, received object at "config.environment"`）。
